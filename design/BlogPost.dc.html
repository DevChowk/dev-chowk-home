Multi-tenancy is a data model decision, not a middleware one

DC
[AUTHOR NAME] [ROLE]

Tenancy strategy tends to get picked in the first week of a project, in a thread that lasts under an hour, and understood somewhere in year two — normally the first time a customer asks where their data physically lives, or the first time one tenant's bad query takes everyone else down with it.

The reason it goes wrong is that "multi-tenancy" gets filed as an access-control problem. It isn't. Access control is the part you can change on a Tuesday. The shape of your data is the part you cannot.

01 — The three shapes

There are really only three, and everything else is a blend. A shared table with a tenant_id column on every row. A schema per tenant inside one database. A database per tenant. They differ in exactly one thing that matters: where the blast radius of a mistake stops.

POLICY.SQL POSTGRES 16 
-- row-level: one bad WHERE clause away from a breach
ALTER TABLE invoice ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON invoice
  USING (tenant_id = current_setting('app.tenant')::uuid);

Row-level security is one forgotten WHERE clause away from being no security at all.

02 — What row-level actually costs

Row-level is the cheapest to build and the most expensive to be wrong about. It gives you one migration path, one connection pool and one backup — and it puts every tenant's rows in the same physical pages, which means noisy-neighbour problems arrive as a performance mystery rather than an isolated incident.

It is still the right default for most products. What changes the answer is regulation, a customer large enough to negotiate, or a workload where one tenant is a thousand times the size of the median.
